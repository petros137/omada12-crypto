# 2.4 Έλεγχος λογισμικού: σχέδιο ελέγχου και test cases

Ομάδα 12 · Μηχανική Λογισμικού 2026-27 · Υπεύθυνος: Απόστολος Δαγκλής (Αναλυτής & Ελεγκτής) · σχέδιο Ε5 (9/11/2026)

**Κατάσταση.** Σχέδιο ελέγχου: όλα τα test cases είναι γραμμένα, οι στήλες **Actual Result** και **Pass/Fail** μένουν
κενές. Συμπληρώνονται στην Ε9 (7/12–13/12), με εκτέλεση πάνω στον τελικό («παγωμένο») κώδικα. Αν ένα TC αποτύχει,
μένει «Fail» με μία γραμμή εξήγηση.

## Πώς γράφτηκαν

- Το **Expected Result** κάθε TC βγαίνει από την προδιαγραφή ([1.5](../P1/1.5-uc-specs/)) και τις απαιτήσεις
  ([1.3](../P1/1.3-apaitiseis.md)), όχι από την εφαρμογή. Τα μηνύματα σε «» είναι αυτά που γράφει η προδιαγραφή.
- **Βασική ροή → θετικό test · εναλλακτική ροή → αρνητικό test · NFR με αριθμό → test μέτρησης.**
  Η στήλη «Είδος» στο § 2 το δείχνει: Θ = θετικό, Α = αρνητικό (με τον αριθμό της εναλλακτικής ροής, π.χ. 8a1), Μ = μέτρηση.
- Όπου μια τιμή εξαρτάται από απόφαση που δεν έχει κλείσει ακόμη (π.χ. 30 s, απόφαση #13), γράφεται η τιμή της
  βάσης και ο αριθμός της απόφασης. Αν η ομάδα αποφασίσει άλλη τιμή, αλλάζει το Expected και το αντίστοιχο JUnit.
- Στήλες όπως ζητά το μάθημα: Test Case # · Description · Test Data · Expected Result · Actual Result · Pass/Fail,
  συν «UC / FR» για την ιχνηλασιμότητα ([`docs/traceability.md`](../traceability.md)).
